# Картотека граждан

Тестовое задание для Frontend-разработчика: дашборд, картотека граждан (100 000 записей, ~75 полей, 5 связанных таблиц) и карточка гражданина. Структура наполнения взята из модулей портала ППК РЭО (обращения граждан, документы, справочники) и переработана под современный интерфейс.

## Что реализовано

- **Обзор** (`/`): KPI-полоса, динамика обращений, статусы открытых обращений, граждане по регионам, возраст и пол, темы обращений, список «требуют внимания».
- **Картотека** (`/registry`): таблица с поиском по ФИО, номеру и телефону, фильтрами (статус, категория, регион, пол, возраст, просрочка), сортировкой по колонкам и счётчиком «найдено X из 100 000». Фильтры и сортировка хранятся в URL.
- **Карточка** (`/registry/:id`): открывается справа от списка. Разделы: общие сведения, контакты и адрес, семья и жильё, образование и работа, льготы и услуги, обращения, документы, история. Редактирование с валидацией и сохранением.
- **Новая карточка** (`/registry/new`): пошаговый мастер (4 шага) на той же схеме полей, что и карточка.

## Стек

| Что | Зачем |
| --- | --- |
| React 18 + TypeScript + Vite | стек из ТЗ, строгие типы без `any` |
| React Router 6 (data router) | вложенные маршруты, `useBlocker` для защиты от потери правок |
| TanStack Query | кэш, отмена запросов, `keepPreviousData`, бесконечная подгрузка |
| TanStack Virtual | список из 100 000 строк рисует ~20 DOM-строк |
| Recharts | графики дашборда |
| Vitest + Testing Library | тесты |

CSS: обычные файлы на токенах (`src/styles/tokens.css`) с префиксами классов. Библиотек компонентов нет, все элементы сделаны вручную.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm test         # юнит-тесты
npm run lint
npm run build
```

Нужен Node.js 18+.

## Структура

```
src/
  app/              оболочка, роутер
  domain/           типы, справочники, схема полей формы, валидация (без React)
  mocks/            генератор данных, фильтрация/сортировка, «сервер» с задержками
  shared/           ui-примитивы, форматирование, хуки
  features/
    dashboard/      дашборд и графики
    registry/       фильтры, таблица, карточка, связанные таблицы
    citizen-form/   форма, которая строится из схемы
    wizard/         мастер создания карточки
```

## Ключевые решения

1. **Масштаб.** Список работает с проекцией из ~17 полей, полная карточка (~75 полей и связанные таблицы) грузится только при открытии. Таблица виртуализирована, страницы подгружаются по 60 записей, фильтрация и сортировка выполняются «на сервере» (в моке), а не в компоненте.
2. **Форма из схемы.** Все поля описаны данными в `src/domain/schema.ts`: тип, обязательность, шаблон, диапазон, условная видимость (`visibleIf`). Карточка и мастер рисуются из одной схемы. Чтобы дойти до 150 полей, достаточно дописать схему. Компонент поля обёрнут в `memo`, поэтому ввод в одно поле не перерисовывает остальные.
3. **Состояние в URL.** Поиск, фильтры и сортировка лежат в query-параметрах: выборку можно отправить ссылкой, при открытии карточки фильтры не теряются.
4. **Несохранённые правки.** При уходе со страницы с изменениями показывается подтверждение (`useBlocker` и `beforeunload`).
5. **Поиск с debounce** 300 мс, запросы отменяются через `AbortSignal`.
6. **Доступность.** Семантичная разметка, skip-link, `role="table"` для виртуализированной таблицы с `aria-sort`, вкладки со стрелочной навигацией, связанные с полями сообщения об ошибках, видимый фокус, `prefers-reduced-motion`.

## Допущения

- Бэкенда нет. `src/mocks/api.ts` имитирует API с задержками. Данные 100 000 граждан детерминированно генерируются в браузере (одна запись всегда одинакова), все они вымышленные. Замена на реальный API сводится к переписыванию 5 функций, которые используют хуки в `features/*/queries.ts`.
- Изменения хранятся в памяти и пропадают при перезагрузке страницы.
- Помесячная динамика обращений на дашборде синтетическая: в реальной системе её отдавал бы агрегирующий эндпоинт. Остальные показатели считаются по сгенерированной картотеке.
- Выбран вариант «картотека граждан». Обращения (help desk) показаны как связанная таблица карточки и в метриках дашборда.

## Что можно улучшить

- Вынести генерацию индекса в Web Worker (сейчас ~0,4 с блокировки при первом открытии).
- Клавиатурная навигация по строкам таблицы стрелками.
- Добавление и редактирование строк связанных таблиц (члены семьи, образование).
- Сохранение черновика мастера и e2e-тесты (Playwright).
- Тёмная тема на существующих токенах, маска ввода телефона, СНИЛС и паспорта.
